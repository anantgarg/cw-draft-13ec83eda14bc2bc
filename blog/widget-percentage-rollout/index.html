Gradual widget rollouts for Crossword

15 September 2026Released
A percentage that stays understandableRamping without changing the meaningStable for a browser and for a verified shopperAttribution and debugging

We built percentage rollouts so a merchant can introduce the Crossword widget to a controlled share of visitors before widening the audience.

Crossword is an AI shopping assistant for ecommerce. Its widget sits directly in the shopper journey, so onboarding a new store deserves a gradual path. A merchant or FDE can now set the share of visitors who receive the widget on a channel. Each visitor gets a stable outcome, while the percentage can move as the rollout progresses.

This feature has one job: control delivery in production. It contains no experiment machinery, declared success metric or analysis step. The operator chooses a percentage and Crossword handles who receives the widget.

A percentage that stays understandable

Small audiences expose a problem with a simple random coin. A 50 percent setting can drift visibly when only a few visitors have arrived. We wanted the configured share to mean something concrete from the start.

The shipped assignment path uses a server-side rota. Under a row lock, it looks at the live counts, calculates which side is short and assigns the next new browser accordingly. At 50 percent, six new assignments produce three in and three out. At 25 percent, sixteen produce four in and twelve out. Assignment follows arrival order, which is the tradeoff behind keeping the split exact at these sizes.

The decision happens before Crossword establishes an identity. A browser outside the rollout does not cause an anonymous contact to be minted simply to learn that the widget should stay off. Existing channels with no rollout rule continue to admit visitors, which keeps deployment order safe.

The browser asks for an assignment once and caches the answer. If the assignment request fails, it falls back to deterministic browser-side hashing. This resolves an easy source of confusion in the implementation: the primary assignment is made by the server and the client-side hash is the failure path. The hash keeps the browser's result stable even when the endpoint is unavailable, though it cannot promise the rota's exact counts.

Ramping without changing the meaning

A rollout freezes the inputs that define its population, including its deployment ID, salt, experiences and strategy. The percentage can move. Raising it only adds recipients.

At rollout start, an operator chooses how the percentage should be interpreted. The default forward mode applies the new percentage from that moment. Lifetime mode steers the all-time average. That distinction matters when a percentage comes down: lifetime correction can stop admitting new recipients while the historical total catches up. The start flow states that consequence so the operator can choose deliberately.

The dashboard also records earlier percentage phases. This gives the current setting its operating context without turning the feature into a results dashboard. Comparison, funnel and money sections existed behind a disabled flag at shipment and are outside this release.

Stable for a browser and for a verified shopper

Browser storage keeps an anonymous visitor on the same side across reloads. Signed-in shoppers can also keep an arm across devices when verified identity stickiness is enabled.

This option is off by default at the workspace level and can be overridden for an individual rollout. It accepts a signed contact token. An email typed into chat does not qualify because it has not been verified.

A second device must receive its initial page-load assignment before the site identifies the shopper. When that assignment disagrees with the contact's stored arm, the operator can choose whether the first arm or the latest arm wins. Crossword moves the participant between the counters instead of counting the same person twice. The current session stays as it is. Storage and the server settle the choice for the next load, avoiding a widget that disappears during a visit.

Attribution and debugging

Rollout context is stamped onto tracking events when they are captured. The arm and deployment ID travel through ingestion into contact events and visits. Capturing the context at the source keeps queued batches tied to the assignment that was active when the activity happened.

For verification, window.__crosswordRollout explains the browser's outcome. It distinguishes a server assignment from a hash fallback, which helps an FDE understand why a visitor did or did not receive the widget. The Rollouts screen also shows the counts handed out on each side, the percentage phases and the ramp control.

The result is a controlled onboarding path for a shopper-facing surface. Merchants can begin with a chosen share, inspect assignment behavior and widen delivery while each browser keeps a stable experience. When verified identity stickiness is enabled, that continuity carries to the shopper's other devices on the next load.
