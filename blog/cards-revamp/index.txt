18:T14d9,<p>Crossword now keeps a fixed library of cards. A merchant chooses a card from that library. The agent fills its fields. We own the structure shoppers see, and we update it for every merchant on the next widget deploy.</p>
<p>On 21 Sep 2026 I ruled that we would always have a card library, that merchants would select from it and that we would not have merchants build their own set of cards. This is that library.</p>
<p>The earlier path had an agent building cards at runtime. Every card was generated fresh, behaved slightly differently and broke in ways we could not always reproduce. Every agent release then needed a design pass on the cards it might render. The library takes that work off the model and off the per-release review.</p>
<p>The library covers the cards already in real use: product, product with variants, carousel, order status, address picker and the related sheets that sit with those cards. A merchant who wants a product card with a size picker chooses Product with variants. That card renders the same way for every merchant. When we improve the size picker, every merchant gets the improvement on the next widget deploy. The agent picks a library card and fills the named fields. It does not invent a new card layout on that turn.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/cards-revamp/01-product-card.png" alt="A product card from the current design reference." /><figcaption>A product card from the current design reference.</figcaption></figure></p>
<h2 id="the-agent-fills-a-known-card">The agent fills a known card</h2><p>With a library card, the model supplies values such as the product name, image, price, rating and available choices. The card definition controls where those values appear and how the card behaves. Field contracts are strict enums. An invalid value fails at the tool boundary, so it does not render as a broken card.</p>
<p>A product card keeps the same layout from one turn to the next. A carousel uses that same structure across a set of results. A related sheet, such as add to cart, follows its own defined steps and stays tied to the card that opened it.</p>
<p>The strict contract is there to stop a class of bug we already knew: a card that sits on a stuck shimmer because an unexpected value made it into the render path. Unknown properties and invalid values are rejected when the card is filled. The agent has a smaller job. It selects the appropriate library card and fills the contract. The widget draws what that contract allows.</p>
<p>Shoppers therefore see a familiar product card or carousel, even as the agent chooses different products from one turn to the next. The agent still decides which card to use and which values to fill. The library decides how that card is drawn.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/cards-revamp/02-product-card-carousel.png" alt="A product carousel from the current design reference." /><figcaption>A product carousel from the current design reference.</figcaption></figure></p>
<h2 id="merchants-pick-from-the-library">Merchants pick from the library</h2><p>Inside Crossword, a merchant starts with the card library. The picker shows the available cards with a preview, grouped by use. Choosing a card creates a linked card based on that library definition. The merchant can then connect the card&#39;s fields to the information the agent will provide. Merchants choose the experience that fits the job. Crossword maintains the underlying structure.</p>
<p>A library definition is shared. When we improve a card, every linked use of that card gets the improvement on the next widget deploy, with no migration and no per-customer version. A linked card stores its library reference and its permitted overrides, so the source card can move forward while the merchant&#39;s connection stays in place.</p>
<p>Design approval now sits on the library itself. An improvement is reviewed once, then reaches every merchant who uses that card.</p>
<p>A library card can also land in the middle of an answer, in the same stacked text-card-text order described in the interleaved-answers post. That timing is separate. This post is about where the card&#39;s structure comes from.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/cards-revamp/03-add-to-cart-sheet.png" alt="An add-to-cart sheet from the current design reference." /><figcaption>An add-to-cart sheet from the current design reference.</figcaption></figure></p>
<h2 id="cards-keep-the-agents-order">Cards keep the agent's order</h2><p>Cards now appear in the order the agent sends them, by default. The channel setting <code>cardHoldMs</code> defaults to 0, so Crossword does not add a text-first delay. If the agent sends a card before its explanation, the live conversation keeps that order. After a refresh, the same order is still there.</p>
<p>Channels used to hold every card for up to 1.2 seconds so that a card-first reply would show text first while it was live. That hold is now optional. A brand that wants the older text-first timing sets <code>cardHoldMs</code> to 1200. That restores the previous 1.2 second hold. This is a change for channels that relied on the old hold always being there. The card itself still comes from the same library.</p>
