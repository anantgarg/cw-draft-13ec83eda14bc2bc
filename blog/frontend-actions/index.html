Frontend Actions give the shopping agent a path into the storefront

20 July 2026Released
The store defines the boundaryA contract before behaviorWhat this changes for shopping assistants

The useful action in a shopping conversation often belongs to the page where the shopper already is.

A store already knows how to add an item to its cart. It knows the current page state and how navigation works. Its browser code owns those operations. An assistant needs a safe, explicit way to ask that code to do something and receive the outcome.

Frontend Actions establishes that interface. In July, we merged the first contract for agent-to-host-app actions into Crossword's widget stack. This first layer defines how a host can describe an action, how an action request reaches the widget and how the outcome travels back over the same widget WebSocket connection.

The store defines the boundary

The central design choice is that the host page owns its actions. Action names and definitions come from the host. The contract does not presume a universal catalog that every merchant must implement.

That matters because storefronts differ. One store may expose an operation for its cart. Another may expose an operation tied to page state. Each host can define the interface that fits its own application instead of forcing its browser behavior through a fixed set of Crossword commands.

The initial contract introduces a FrontendActionDef and three WebSocket frames. Together, they describe the full exchange without moving executable browser code across the connection.

The first frame is client_actions_declare. It travels from the widget to the server and carries metadata for the actions registered by the host. The handler stays in the browser. This keeps ownership clear: the declaration tells the system what is available while the host retains the code that performs the work.

The second frame is agent_action_request. It travels from the server to the widget when the agent invokes one of those actions. The request gives the browser side of the integration a defined message to receive and handle.

The third frame is agent_action_result. It travels from the widget to the server with the outcome. An actionId correlates that result to the request. The payload records whether the operation succeeded and carries either a result or an error.

A contract before behavior

We deliberately shipped this as a contract-first change. The pull request froze the message shapes and wired them into the client and server frame schemas plus the contract exports. It did not add the runtime behavior that executes host handlers.

That sequence is important in a system with code on both sides of a live connection. The widget and server need to agree on direction, correlation and result shape before they can implement the surrounding behavior independently. A stable interface gives both sides the same source of truth.

It also creates a clean separation of responsibilities. Crossword can reason about declared capabilities and structured outcomes. The storefront remains responsible for the browser operation itself. The server sees metadata and results. The browser keeps the handler.

The same structure supports actions with very different outcomes. A host operation might eventually return page state, report that a cart operation completed or return an error the agent can use. The contract only defines the exchange. The host decides what its registered action means.

What this changes for shopping assistants

Conversation is useful for discovery and explanation. Shopping also includes operations inside a merchant's application. A shopper may want the assistant to help while staying in the page they are already using. Frontend Actions gives our widget and server a shared language for that class of interaction.

For merchant teams and FDEs, the model is direct. The host declares metadata for the actions it chooses to expose. Requests arrive through a typed frame. Results return with an identifier that ties each outcome to the corresponding request. The integration boundary follows the storefront's existing ownership of browser behavior.

For shoppers, the intended experience is continuity. They can talk with the assistant in the store context while the surrounding page remains the place where store operations happen. Once runtime handling is built on the contract, the agent can use a declared host capability and continue with the returned outcome in context.

There are limits to what this first merge represents. It defines and exports the protocol. Runtime execution, timeout behavior, reconnect behavior, merchant controls and shopper-facing status treatments require their own implementation evidence. We are keeping those claims separate from this contract release.

The work that shipped is foundational and specific: a typed declaration, a typed request and a correlated typed result on the widget WebSocket. That gives the agent, widget and host page an explicit interface for the storefront actions that later runtime work can execute.
