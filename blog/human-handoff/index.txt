18:T167e,<p>A shopping agent needs to know when a conversation should move to a person. We built Human Handoff in Crossword so that escalation is part of the conversation instead of a dead end.</p>
<p>This matters in ecommerce because a shopper can start with a product question and reach a point where a person should step in. The agent needs a clear way to ask for help. The operator needs the context to continue. The shopper needs to understand who is responding.</p>
<p>We designed the handoff around those three views of the same moment.</p>
<h4 id="the-agent-can-request-help-without-abandoning-the-conversation">The agent can request help without abandoning the conversation</h4><p>An FDE can configure what happens when Crossword requests a human. The handoff configuration can let the agent continue answering while the request waits or hold the conversation for an operator. It also accepts guidance for that behavior.</p>
<p>That distinction is practical. Some conversations can keep moving while they wait. Others need a person before the next response. The configuration makes that choice explicit instead of burying it in the prompt.</p>
<p>When a conversation enters the queue, the team sees it in the inbox. Queue, My chats and Unresolved views are backed by the same live conversation list. New and unread counts help operators see where attention is needed. The board receives workspace-scoped updates over a server-sent event stream, so a new request can appear without a five-second polling loop.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/human-handoff/01-new-handoff-arrives.png" alt="A new handoff request in the current Inbox design reference." /><figcaption>A new handoff request in the current Inbox design reference.</figcaption></figure></p>
<h4 id="a-person-takes-over-with-the-conversation-in-front-of-them">A person takes over with the conversation in front of them</h4><p>The operator can assign a queued conversation, claim it and reply from the conversation view. The inbox resolves the identity of the person who claimed the chat. A conversation can also be reassigned when another teammate should handle it.</p>
<p>The right rail gives the operator useful context. It includes the contact record, past conversations and a conversation summary. Past conversations open in the appropriate inbox view. The rail can be resized when the transcript needs more room.</p>
<p>The summary is refreshed around handoff and decision activity. It reads the full conversation while excluding system transition markers. That keeps operational events from becoming part of the shopper&#39;s story.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/human-handoff/02-assigned-human-chat.png" alt="An assigned conversation in the current My chats design reference." /><figcaption>An assigned conversation in the current My chats design reference.</figcaption></figure></p>
<p>This is where continuity matters. An escalation should preserve what the shopper already said and what the agent already did. The operator can read the exchange, use the summary and respond without asking the shopper to restart.</p>
<h4 id="the-shopper-can-see-the-human-behind-the-reply">The shopper can see the human behind the reply</h4><p>Each support agent can have a display name and avatar. Crossword resolves that identity from the support profile, then the account name and then the email. Human replies use that identity in the shopper widget and the dashboard transcript labels the reply with the person&#39;s name and &quot;Human agent.&quot;</p>
<p>A workspace can also configure a join announcement. When an operator takes over or claims the conversation, Crossword emits a dedicated handoff join event. The shopper sees the announcement and it remains after reload. The operator sees the same transition as a centered divider in the transcript.</p>
<p>The event has its own subtype, which separates it from internal system rows. Internal rows stay hidden and system rows are excluded from list previews. The visible marker describes a real transition without leaking the machinery behind it.</p>
<p>When the operator returns the conversation to Crossword, the transcript receives a matching handback marker. The AI then receives the customer and human exchange as context, with human turns identified as support-agent replies. That attribution keeps the next agent response grounded in who said what.</p>
<p>Join and handback markers are deferred when a run is already in flight. This avoids inserting the transition ahead of work that has not finished. We are also deliberately leaving mid-reply takeover out of this description. The shipped flow does not establish that an operator can interrupt an answer cleanly while it is being generated.</p>
<h4 id="human-handling-remains-visible-after-the-moment-has-passed">Human handling remains visible after the moment has passed</h4><p>A handoff is part of the operational history of a conversation. In the runs timeline, AI runs and human-handling segments appear together in time order. A human segment shows who handled the conversation, the messages exchanged and when the conversation returned to the AI.</p>
<p>Teams can filter runs with a Human handled filter and see a Human badge on a run whose session was handed off. This gives the team a way to find these conversations later without reconstructing the handoff from message text.</p>
<p>The result is a single conversation that can move from Crossword to a person and back with identity, context and transition markers intact. The shopper sees who is replying. The operator gets the transcript and summary needed to continue. The AI can use the human exchange when it resumes.</p>
