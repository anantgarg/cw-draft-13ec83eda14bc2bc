15:T1b3f,<p>We built the Crossword browser extension for Safari on iPhone so shoppers can bring an AI shopping assistant into the stores they already visit on mobile.</p>
<p>Crossword helps ecommerce shoppers explore products and get answers in a conversation. Our desktop browser extension already carried that experience across merchant sites. The Safari port brings the same idea to iPhone, where the browser, extension model and packaging rules are different.</p>
<p>One status detail matters here. The iOS Safari port is built on an open feature branch, while the two implementation pull requests remain open and App Store publication is not confirmed in the sources available for this post. This article describes the product we built. It does not announce a store listing.</p>
<h4 id="a-familiar-shopping-flow-on-a-different-extension-platform">A familiar shopping flow on a different extension platform</h4><p>The shopper enables Crossword in Safari and gives it website access. On a store with a Crossword workspace, the widget starts on the page. The extension menu also includes an explicit <strong>Open Crossword</strong> button, along with loading, error and setup states.</p>
<p>From there, the experience is the Crossword chat shoppers already know. They can open the assistant, ask about products and receive answers with product cards. The implementation was tested on a physical iPhone XS Max running iOS 18.7.10, where the production widget loaded from <code>widget.crswrd.ai</code> and returned product cards in chat.</p>

<p>Safari made the port more interesting than wrapping the desktop extension in an iOS project. Safari masks extension file addresses when page code reads them. It also blocks extension module imports from the widget&#39;s embedded chat frame. Both behaviors stopped the widget from rendering even though the initial extension scripts had loaded.</p>
<p>We added a bridge that passes the real widget address into the page. The build also prepares same-origin copies of the required widget modules for the embedded frame. These are narrow, checked patches. The build stops if the upstream bundle changes in a way that makes those patches unsafe to apply.</p>
<p>That last part matters. Browser differences often produce fixes that appear to work until the next build changes a filename or import. Failing the build gives us a clear signal to inspect the integration again.</p>
<h4 id="widget-releases-can-reach-safari-on-the-next-page-load">Widget releases can reach Safari on the next page load</h4><p>The Safari extension loads the widget from Crossword&#39;s widget server, using the same general delivery model as a website embed. A widget release can therefore reach an iPhone on the next page load. Changes to the extension shell, its permissions or the native setup app still require a new app build.</p>
<p>We also kept a bundled copy of the widget as a fallback for pages that block the server script. The strict Content Security Policy case remains an open validation item, so we are treating that fallback as work that still needs broader verification.</p>
<p>The extension resolves a store through Crossword&#39;s public widget lookup API. That lets it work with a store that has a Crossword workspace. If Safari has not granted access to the API host, the extension can use its bundled store list as a fallback.</p>

<p>Developer builds also proved the live delivery path against Crossword&#39;s staging widget and API servers. The public build is configured for production Crossword domains only. Server URLs must use HTTPS and the implementation rejects domains outside Crossword&#39;s allowed domains.</p>
<h4 id="setup-belongs-in-the-product">Setup belongs in the product</h4><p>An iPhone extension has an activation step that a normal website widget does not. We built a native setup flow around it: welcome, turn on the Safari extension, grant website access and confirmation that setup is complete. The flow follows the extension&#39;s actual state. If the extension is switched off, the app returns to the enablement step. Once setup is complete, reopening the app goes directly to the completed state.</p>

<p>The extension still needs permission to run on merchant websites. That broad access is required because a Crossword workspace can belong to any merchant domain. The product explains the setup instead of leaving the shopper to infer it from Safari settings.</p>
<p>The current port targets iPhone and requires iOS 18 or later. The build packages the Safari web extension inside an iOS app and includes the widget bundle, the extension popup and the native setup experience. Automated extension tests pass on the branch, and the code has also been compiled for the iOS simulator and exercised on a physical iPhone.</p>
<p>There is more validation to finish. The sources leave testing across additional stores open, along with the strict policy fallback and the decisions required before a public release. Those checks are part of shipping this responsibly because merchant sites vary in their permissions, page policies and storefront code.</p>
<p>For merchants, the work extends Crossword&#39;s browser experience to shoppers who browse stores in Safari on iPhone. For shoppers, the result is concrete: enable the extension, visit a store with a Crossword workspace and open the same product conversation from the page they are already viewing.</p>
