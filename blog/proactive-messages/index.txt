15:T16e5,<p>I have watched a familiar problem repeat across ecommerce sites. A shopper spends time browsing, the store has useful context and the assistant waits for the shopper to type first.</p>
<p>We built Proactive Messages so Crossword can start with a relevant message when a merchant-defined rule fires. The first shipped system covers the full path from a rule to delivery in a connected widget. It gives our team a practical way to configure when the assistant should reach out, what it should say and how that message should appear.</p>
<p>The clearest example is inactivity. A merchant can create a rule under <strong>When it sends</strong>, choose <strong>After a quiet spell</strong> and set a window from 1 to 60 minutes. The rule can also define which tracked events restart the clock and which events stand the rule down. If a shopper keeps browsing through a reset event, the deadline moves. If the shopper starts a chat and that event is on the stand-down list, the message is canceled.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/proactive-messages/01-inactivity-nudge.png" alt="The current design reference for a proactive inactivity nudge." /><figcaption>The current design reference for a proactive inactivity nudge.</figcaption></figure></p>
<p>That sounds like a timer. The implementation has to be more disciplined than that.</p>
<p>We use lazy evaluation. Arming a quiet-spell rule writes one watch record and one delayed alarm. At the deadline, Crossword reads the clock once and decides whether the rule still qualifies. We do not poll every shopper or add work to each visitor event. The rule&#39;s enabled switch and the workspace pause control are checked at the deadline, so a watch already counting down can still be stopped.</p>
<p>Reachability is checked before message composition. If the shopper is absent, the system avoids an unnecessary model call. Once a message is ready, Crossword stages it for the connected widget session and records the delivery result. The transport is scoped to the contact, with conversation information carried on each frame so the right message reaches the right place.</p>
<h2 id="the-widget-decides-how-to-present-each-message">The widget decides how to present each message</h2><p>Delivery is only half the job. A proactive message can arrive while the panel is closed, while it is open on the relevant conversation or while the shopper is looking at another conversation.</p>
<p>Each message carries its display policy. The widget resolves that policy against its current panel, conversation and activity state. It can show a floating teaser, place a banner above the widget or append the message in the conversation. Product safety clamps are applied after that resolution.</p>
<p>The proactive card uses the same visual language across the floating teaser and the open-state banner. It includes the sender line and can include reply chips. Its arrival uses a short pop animation and an optional one-shot shake. Reduced-motion preferences are honored. Dismissing or replying settles the card and a configured time to live limits how long it remains relevant.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/proactive-messages/02-resting-widget.png" alt="The current resting widget state before a proactive nudge appears." /><figcaption>The current resting widget state before a proactive nudge appears.</figcaption></figure></p>
<p>The details around interaction matter. A message configured with a tap reply sends that reply when the shopper taps it. If a transient proactive message is waiting and the shopper writes in the composer, the message is promoted into the transcript above the shopper&#39;s reply. That keeps the exchange in the order the shopper actually experienced it and gives the agent the same context.</p>
<p>The transport also maintains a durable read marker. An unread proactive message can keep the launcher indicator through a refresh. A banner for another conversation can navigate the shopper to that conversation without announcing itself again after the move.</p>
<h2 id="rules-have-outcomes-not-guesses">Rules have outcomes, not guesses</h2><p>The rules engine records what happened to an attempt. A message that reached the visitor is different from one that was superseded, canceled or could not reach an offline visitor. That distinction is important for rules intended to fire once. Outcomes where nothing reached the shopper do not consume the rule&#39;s one opportunity.</p>
<p>There are operational controls around the same path. Individual rules can be enabled or disabled and a workspace can pause proactive delivery. The quiet-spell implementation also separates its watch work from the main event ingestion path. This gives our team a clearer place to inspect whether a watch is counting down, moved because of activity, stood down or proceeded to send.</p>
<p>We also capped the context snapshot used during composition. Proactive outreach needs enough context to be useful while keeping the input bounded. The send path preserves message sequence when building AI history, including cases where records were created only microseconds apart. It also inserts the correct role boundary so a new outreach cannot be merged into an earlier assistant response.</p>
<p>Proactive Messages gives Crossword a controlled way to begin a useful exchange from live shopping behavior. For an inactivity rule, the merchant defines the quiet window and the events that reset or cancel it. Crossword evaluates that rule at the deadline, checks whether the shopper can be reached, composes within bounded context and hands the widget a complete display policy. The shopper sees a nudge that can open into a correctly ordered conversation and any configured tap reply is sent as part of that exchange.</p>
