15:T11b7,<p>Two changes now shorten Crossword&#39;s own part of the widget boot and stop a class of missed mounts. There is no new merchant setting. The existing embed is enough.</p>
<p>The first change starts the chat file downloading as soon as channel config says chat is on. The loader adds a modulepreload link for the chat chunk, which the PR describes as about 970 KB, so that download overlaps the wait for a tracking session and the frame&#39;s later hops. The preload fetches and compiles the chunk into the host page&#39;s module map. It does not evaluate the chunk on the host page. When the frame then imports it, the request can hit the HTTP cache. The chunk is served as immutable. A build plugin stamps the hashed chunk name into the entry and fails the build if it cannot.</p>
<p>The second change waits until the page is parsed before mounting the chat iframe. The loader used to append the iframe to <code>document.body</code> as soon as it decided chat was on. An embed that boots in the page&#39;s <code>&lt;head&gt;</code> could hit a missing body and that page view would have no chat. While the document is still loading, the loader now waits for <code>DOMContentLoaded</code>, so the iframe lands after the host&#39;s markup. A page that is already parsed mounts at once. The loader re-decides with the latest config, never mounts twice and cancels the work if chat is turned off.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/reduce-time-to-load-the-widget/01-channel-install.png" alt="The channel Install tab, where a merchant places the embed." /><figcaption>The channel Install tab, where a merchant places the embed.</figcaption></figure></p>
<h2 id="what-we-measured">What we measured</h2><p>On live sites the launcher often takes about 3 to 8 seconds to appear. Most of that time is on the host page, not inside Crossword. About 2 seconds is Crossword&#39;s own serial boot. This work trims part of that Crossword portion. It does not remove host-side waits.</p>
<p>The measured figures below come from PR #1255. The setup was a CDN stand-in with brotli and immutable headers, the production API, an internal test workspace with tracking on, and a median of three runs. Only the network was throttled, not the CPU.</p>
<ul>
<li>A returning visitor on desktop went from 1.68 seconds to 1.30 seconds.</li>
<li>A returning visitor on a throttled phone (1.6 Mbps) went from 3.26 seconds to 2.76 seconds.</li>
<li>A first visit on desktop went from 1.70 seconds to 1.39 seconds.</li>
<li>A first visit on a throttled phone went from 3.44 seconds to 2.94 seconds.</li>
</ul>
<p>With tracking off there is no gap for the preload to fill, so timing is unchanged. Those figures are from a test page that did not itself run heavy deferred host scripts. They should be read with that setup, not as a promise for every storefront.</p>
<h2 id="a-safer-mount-and-a-little-less-work-at-boot">A safer mount, and a little less work at boot</h2><p>Waiting for the page to be parsed was a deliberate choice. Placement comes before speed here. The iframe is not attached to a body that does not exist yet, and a shopper on an early-booting embed still gets a chat. The documented guidance remains to place the embed before the closing <code>&lt;/body&gt;</code> tag.</p>
<p><code>DOMContentLoaded</code> fires only after the host&#39;s own deferred scripts have run. On a page with a heavy deferred bundle, even an embed placed before the closing body tag now waits for those scripts. That trade-off was known when this shipped. A later idea, to mount as soon as the document is interactive, is not part of this work.</p>
<p>The boot also does a little less duplicate work. When the loader reports the same page the frame already started on, the frame no longer fetches suggestion chips a second time.</p>
<p>On a page that page rules have already hidden, the early chat-chunk download is skipped. That interaction is part of the page-rules work. This post is about the preload and the safe mount.</p>
<p>For a shopper, the widget can start sooner on pages where chat is on, and it no longer disappears when the script runs before the body exists. For a merchant, nothing new has to be configured. The same embed, published in the usual place, picks up both changes.</p>
<p>These two changes landed on 15 Oct 2026 and were included in the week-4 widget release the same day. A store already running the current widget bundle picks them up with that release. There is nothing extra to turn on.</p>
