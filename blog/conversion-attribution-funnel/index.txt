15:T180b,<p>Attribution gets useful when every event carries enough context to explain what happened.</p>
<p>The work covers the path from a widget session through suggestions, messages and interactive cards. It gives operators cleaner facts for analysis without pretending that every part of a purchase funnel is already observable.</p>
<p>The basic problem is easy to state. A click count says very little on its own. An operator needs to know what the shopper saw, which option they selected, where the interaction happened and which conversation produced it. Those facts also need to survive malformed client data, duplicate impressions and large payloads.</p>
<h4 id="start-with-where-the-interaction-happened">Start with where the interaction happened</h4><p>Tracked events can now include a server-derived device type: desktop, mobile or tablet. An extensible metadata field can carry browser, operating system, engine, screen size and viewport size.</p>
<p>The server classifies the device from the User-Agent across browser tracking, widget telemetry and server-emitted events. The client supplies only screen and viewport dimensions. Those values are validated at intake and again at the ingest boundary. Missing or invalid details stay blank. Device information is useful for analysis, never as a trust signal.</p>
<p>Operators can use these dimensions in cohorts, traits, analytics and proactive rules. Activity also shows device context on individual events. That context tells an operator whether the behavior happened on a phone, tablet or desktop.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/conversion-attribution-funnel/01-buyers-design-reference.png" alt="Current dashboard design reference for buyer analysis. This is related analytics context, not a conversion funnel screen." /><figcaption>Current dashboard design reference for buyer analysis. This is related analytics context, not a conversion funnel screen.</figcaption></figure></p>
<h4 id="record-what-the-widget-offered">Record what the widget offered</h4><p>Suggestion chips now produce an impression event for every displayed chip and a click event when a shopper chooses one. Both events share a generated set ID. They also carry the chip&#39;s source, position and text, which lets the displayed set join to its clicks.</p>
<p>The widget emits each impression once per rendered set while the browser tab is visible. The server validates the source, position, set ID and text before accepting the frame. The ingest consumer masks chip text. This gives an operator the inputs needed to compute click-through by suggestion source while keeping the event vocabulary and validation on the server.</p>
<p>The same release made conversation tracking more precise. Loading the widget produces <code>session_started</code>. <code>conversation_started</code> is reserved for the visitor&#39;s first message. Per-message events cover visitor messages, agent messages, proactive messages received and CSAT offers.</p>
<p>Those message events carry structured facts such as the message ID, sequence, role, kind, card template, agent ID and proactive stamp. They do not store message text. A conversation ID connects eligible widget events back to the conversation that produced them.</p>
<h4 id="connect-cards-to-the-actions-merchants-care-about">Connect cards to the actions merchants care about</h4><p>Cards already produce built-in view and click events. Card authors can now attach a workspace event to the card or to a clickable control inside it, then map selected card values into that event. The author event is recorded alongside the built-in event.</p>
<p>For a product list, the card can map the list as one field with indexed item properties. For a control inside a repeated item, the server resolves the selected item from the rendered node and records that item&#39;s mapped values as scalars. The client does not choose an item index. Field types come from the card slot declaration.</p>
<p>This matters because attribution needs a stable join between an interaction and the content that caused it. A product tap can carry the declared product fields that an operator selected during setup. Creating or binding these events requires tracking management permission in addition to agent editing permission.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/conversion-attribution-funnel/02-cart-design-reference.png" alt="Current dashboard design reference for cart analysis. This does not represent a shipped attribution funnel." /><figcaption>Current dashboard design reference for cart analysis. This does not represent a shipped attribution funnel.</figcaption></figure></p>
<p>The implementation also protects the base event when a card payload grows. Optional whole-card context is removed first if the widget payload would exceed its bound. Mapped values are removed only if the base facts still cannot fit. Message and element identifiers remain, preserving the join back to the card interaction.</p>
<p>Operators can turn the built-in card pair down per card, choosing both events, views only or neither. The control makes the resulting tracking cost explicit.</p>
<h4 id="keep-the-boundary-honest">Keep the boundary honest</h4><p>The event catalog exposes these additions through the existing per-event switches. The event editor distinguishes events that originate from a page, card or integration. Platform fields are rendered from the shared registry in Activity, the event drawer and the editor.</p>
<p>This work improves the evidence available for discovery, suggestion engagement, conversations and card interactions. It also adds dimensions that can support segmentation and analysis.</p>
<p>Purchase and refund capture require a trusted source. The browser does not capture those events by design, and this work did not add that source. So we are keeping the product claim at the level the data supports: Crossword records richer, joinable interaction events and gives operators clearer inputs for attribution. A complete purchase funnel needs the purchase side of that chain to be present.</p>
