Separating implementation traffic from customer conversations

15 September 2026Released
Give every session a sourceA filter operators can understandSmall controls need complete data pathsWhat this changes for implementation reviews

Every conversation in an AI shopping assistant looks important when it lands in the same inbox.

During an implementation, that creates a specific problem. The team testing Crossword through the demo extension uses the same workspace that will receive conversations from the website embed. Both kinds of traffic reach the operator views together. A person reviewing conversations then has to work out which sessions came from implementation work and which came from shoppers on the site.

We record a simple distinction for that traffic: record where each session started and carry that context into the dashboard.

That sounds like a filter. Most of the work sits underneath it.

Give every session a source

The path starts where the widget is injected. The extension stamps its version on the widget. The widget then sends a client block during both bootstrap paths with the surface, widget version and extension version. The API records the surface and build information on the session.

The surface has two meanings: an extension session or a website embed session. It is descriptive context. It does not grant access, change metering or gate behavior.

That distinction matters because the traffic previously arrived with the same embed key, the host page origin and a web channel. By the time it reached the API, the two paths looked the same. Recording the source at bootstrap gives the rest of the system a reliable value to use.

The design also carries the surface through the widget token and into tracked contact events. That keeps the session record and its event trail aligned. Build identifiers give the team another useful clue when reviewing an implementation session. They can see which widget and extension versions produced it.

A filter operators can understand

The dashboard keeps all traffic visible by default. An Extension pill identifies a conversation created through the implementation extension. An Extension traffic control provides three choices: All traffic, Extension only and Hide extension.

The visible default is deliberate. A new classification should not silently remove conversations from an operator's view. When an operator chooses a narrower view, an "N hidden" count makes the effect explicit. A filtered view has a route back to all traffic.

This treatment is on Conversations and AgentOps. Those are the places where merchants and forward deployed engineers inspect sessions, runs and events. The conversation rail adds a Surface row plus the widget and extension build identifiers, so a person investigating one conversation can inspect its provenance without leaving the record.

The filter is separate from existing test traffic behavior. Surface answers how the client reached Crossword. Test traffic can represent a different classification. Keeping those concepts separate avoids turning one control into a collection of loosely related meanings.

Small controls need complete data paths

Filtering an inbox is easy when the data already exists. Here, the source has to survive the entire path from an injected widget to the operator's screen.

The path covers the extension stamp, the widget contract, session storage, the token claim, event ingestion, API queries and the dashboard controls. API queries also account for older sessions with no recorded surface. Those records still belong in the non-extension view. The hidden count uses the same base filters and time window as the visible results, so the count explains the current view instead of describing a different query.

The migration is additive. It introduces session fields for surface and client details plus a surface field for contact events. There is no backfill, so older sessions can continue to have no surface value.

That compatibility is important during rollout. New widgets can send the client block while older API or dashboard versions ignore additive fields. A rollback can return services to an earlier image while leaving the added columns unused.

What this changes for implementation reviews

The operational benefit is straightforward. A merchant or forward-deployed engineer can focus on extension traffic while validating an implementation. The same person can hide that traffic while reviewing conversations from the website embed. When they open a specific extension conversation, the rail provides the source and build context needed to investigate it.

It also gives support work a cleaner starting point. A session is tied to the path that created it and to the client builds recorded at bootstrap.

Older sessions with no surface value stay in the non-extension view. There is no backfill, so those earlier records simply have no surface. New widgets send the client block; a narrower filter never silently drops conversations that have no surface value.
