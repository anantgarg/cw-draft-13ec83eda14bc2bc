15:T1855,<p>This feature is in review and has not shipped. The draft below describes the behavior we designed and built on the feature branch.</p>
<p>Crossword already opens as a floating window or a full-height sidebar. The sidebar currently covers part of the store page. That is simple, but it can hide the exact context a shopper needs while asking a question: a price, a filter, a product card or the cart.</p>
<p>The new design gives merchants a second sidebar layout called <strong>Make room beside the page</strong>. When a shopper opens Crossword on the right, the page moves left. When Crossword opens on the left, the page moves right. The store continues rendering in the space that remains beside the conversation.</p>
<p>The browser viewport itself does not change. We move the page boundary while leaving the store&#39;s own responsive behavior alone. Wide content follows the store&#39;s existing overflow rules. Sticky page elements generally move with the page. The implementation also makes a best effort to move fixed bars, banners and buttons out of the reserved space.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/resizable-push-sidebar/01-sidebar-right.png" alt="Current right sidebar design reference" /><figcaption>Current right sidebar design reference</figcaption></figure></p>
<h4 id="a-sidebar-that-behaves-like-an-adjacent-window">A sidebar that behaves like an adjacent window</h4><p>The useful part of a push layout is the relationship between both surfaces. The page and the conversation should feel connected as the panel opens, closes and changes width.</p>
<p>The designed open motion takes 420 milliseconds. Closing takes 500 milliseconds. The page follows the sidebar with the same easing. During a resize, the reserved page space updates with the panel width. A thin line separates the two surfaces and a narrow gutter gives the shopper a reliable place to grab.</p>
<p>The push behavior applies on browser windows at least 800 pixels wide. Below that threshold, the sidebar covers the page. At 640 pixels or less, Crossword uses the normal chat window. These boundaries keep the remaining store page usable and preserve the existing small-screen experience.</p>
<p>The implementation keeps at least 400 pixels of the store visible on wider screens. A page is never zoomed to make it fit. If a store theme has content wider than the remaining space, its own layout and overflow behavior decide what the shopper sees.</p>
<p>The feature also handles navigation while a remembered sidebar is open. On eligible pages, the loader reserves the space before the full chat arrives. This reduces the visible jump between store pages. If the chat fails to load, the page returns to full width. If browser storage is blocked, the sidebar still opens at the configured default width and can still be resized for that page.</p>
<h4 id="width-is-part-of-the-merchants-design">Width is part of the merchant's design</h4><p>The dashboard work adds controls under Style and Sidebar. A merchant can choose <strong>Cover the page</strong> or <strong>Make room beside the page</strong>, set a default width and decide whether shoppers can resize the sidebar.</p>
<p>The default width can be set from 320 to 720 pixels. When shopper resizing is enabled, the merchant can choose <strong>Half the window</strong> or a fixed widest width from 400 to 1200 pixels. The effective width still preserves at least 400 pixels of the store page. The dashboard rejects a fixed maximum that is narrower than the default.</p>
<p>Merchants can also set the resize line color, choose a thickness from 1 to 6 pixels and keep the line visible. The dashboard preview uses a mock store page and a virtual 1440 pixel window so the merchant can see cover and push behavior inside the smaller preview pane. Preview dragging is temporary and does not save a shopper width.</p>
<p>These layout, width and resize choices take effect for a visitor on the next page load. Line styling can update on an open page because it does not change the panel geometry.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/resizable-push-sidebar/02-sidebar-left.png" alt="Current left sidebar design reference" /><figcaption>Current left sidebar design reference</figcaption></figure></p>
<h4 id="resizing-is-designed-for-a-mouse-keyboard-and-touch">Resizing is designed for a mouse, keyboard and touch</h4><p>When resizing is enabled, a shopper can drag the sidebar&#39;s inner edge. The same edge works as an accessible divider: arrow keys change the width by 16 pixels, Home moves to the narrowest allowed width and End moves to the widest. Screen readers receive the resize control and its current pixel width. Touch screens at least 800 pixels wide get a wider grab area.</p>
<p>The chosen width is remembered in that browser for that store&#39;s chat. It stays between the merchant&#39;s default and widest settings while also respecting the space required for the store. A wider conversation keeps its messages in a centered reading column, while product rows and the cart use that column&#39;s full width.</p>
<p>There is an important history here. An earlier drag-resize change was merged on 29 October with a 400 to 576 pixel range and a half-window ceiling. The repository then removed that work from the staging branches before release. The current feature branch restores resizing inside the broader width model and adds the push layout, dashboard width controls, loader behavior and page integration. The frame-link portion was merged into the project branch on 31 October. The umbrella pull request remains open.</p>
<p>We built the default as cover mode with resizing off. Existing channel configurations therefore keep their current layout. The new behavior begins only after a merchant chooses it and publishes the setting.</p>
<p>The review work covers both left and right walls, remembered widths, blocked storage, page navigation, fixed bars and recovery when the chat fails. The Storybook placement references show the sidebar states and launcher drag variants. They do not demonstrate a host page being pushed, so the media plan below keeps that limitation explicit.</p>
