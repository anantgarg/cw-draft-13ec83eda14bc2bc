Data tables give Crossword agents a governed view of merchant data

21 July 2026Released
A working surface for merchant dataSave the query onceSearch by meaning and derive useful columnsAccess belongs in the data path

I have seen the same problem appear in every serious shopping agent project: the useful answer lives in merchant data, while the agent starts with a prompt.

A catalogue can sit in one system. Order data can sit in another. An operator may know the exact query that answers a common shopper request. The agent still needs a reliable way to reach that information with the right access.

We built Data Tables in Crossword to make that connection explicit. Crossword is an AI shopping assistant for ecommerce. Data Tables gives the people operating it a workspace for connecting data, inspecting rows, preparing queries and deciding what each agent can use.

The surface lives in the merchant dashboard. Shoppers never have to understand the table behind an answer. They experience the result when the agent can use current merchant data during a conversation.

A working surface for merchant data

An operator can create a table, define its columns and work with its rows from the dashboard. The rows grid supports inline editing, type-aware inputs, adding and deleting rows, sorting and search. Locked tables remain readable while writes are blocked.

The column setup keeps a human-facing display name alongside a safe database identifier. When someone adds a column called "Full Name," for example, the interface previews the stored identifier before the change is made. This small detail matters when the same table has to work for an operator, a query and an agent.

Data can also arrive through connectors. The shipped file-upload flow accepts a JSON document, detects fields and lets the operator map them into a managed table. It reuses the same column inference, typing, indexing and table registration path used by JSON ingestion. The resulting table returns to the same workspace surface as manually managed data.

Save the query once

Raw rows are useful for inspection. Agents need a narrower contract.

Stored queries let an operator define that contract. A query has declared parameters and Crossword validates the inputs before execution. System values such as the workspace, agent, run and contact are injected by the runtime. The agent cannot replace them through its own arguments.

The dashboard includes an editor and a playground. Operators can preview reads and test writes. Write previews roll back by default, with an explicit path to commit. Read results can be capped and executions produce audit records with the mode, source, tables and row count.

The next step is binding. In an agent's Data section, an operator attaches table access and stored queries. Table access can be assigned by action, including find, insert, update and delete. Query bindings control read or write mode, delivery as a tool or prompt context, cadence for prompt delivery and an optional row cap.

That last part changes how I think about prompts. A prompt can refer to a stored query without carrying the merchant's data inside the prompt itself. Crossword resolves the binding at runtime. Tool bindings are exposed to the agent as executable tools. Prompt bindings run on their configured cadence and place the result into the assembled prompt.

Search by meaning and derive useful columns

Some tables need a search layer. An operator can enable semantic search for a table and choose the columns that should be embedded. Crossword maintains row embeddings asynchronously, including a backfill when search is enabled and incremental updates as data changes. The agent receives a search tool only for a table it has been granted.

Search returns live rows after finding relevant records. That keeps the index focused on retrieval while the table remains the source used for the result.

Enrichment adds derived columns to the same data model. An operator chooses source columns and the derived columns to generate, reviews a projected call count and confirms the backfill. The pipeline can then process changes as they arrive. Enrichment and semantic search are optional controls at the table level.

Access belongs in the data path

Prompt instructions are a weak place to enforce data permissions. Crossword carries permissions into query registration and execution.

Each workspace has isolated data-plane roles. Each agent receives only the table actions and stored queries assigned to it. For a table linked to a contact, PostgreSQL row-level security scopes agent reads and writes to the verified contact being served. The runtime sets that verified identity in the database session. An anonymous or unverified request has no contact scope, so the policy fails closed.

Operators still need to manage the complete table. Dashboard row operations use a separate workspace analyst role while agent paths continue through the scoped roles. This preserves an operator's working view without weakening the agent boundary.

The same system records data access for review. Operators can filter access logs and follow a record back to the related agent run. Together, grants, bindings, database roles, row policies and audit records make table access a product setting with an execution path behind it.

Operators can inspect the source, shape the query, assign the capability and review its use from the dashboard. The shopper receives an answer grounded in the data that the agent was allowed to reach.
