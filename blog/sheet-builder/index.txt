18:T1655,<p>We built Crossword as an AI shopping assistant for ecommerce. A conversation is useful when the agent can answer a question, find the right product and help a shopper move forward. Some moments still need structure. An email address has to be confirmed. A phone number has to be verified. A required field has to be completed before the conversation continues.</p>
<p>Sheet Builder gives those moments a native surface inside the widget.</p>
<p>It is a stepped bottom sheet built on the same content model we use for cards. The sheet is a node tree with client state and action frames, so the interaction can carry data, validate a step and submit a result without sending the shopper into a separate form.</p>
<p>That shared model matters to us. A sheet can feel like part of the conversation because it uses the widget&#39;s existing interaction primitives. The shopper keeps the context of the chat while the sheet creates enough focus for a structured task.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/sheet-builder/01-sheet-primitive.png" alt="The Sheet primitive in the current Crossword design reference." /><figcaption>The Sheet primitive in the current Crossword design reference.</figcaption></figure></p>
<h2 id="three-ways-to-open-the-same-surface">Three ways to open the same surface</h2><p>The implementation supports three opening mechanisms. A front-end action can open a sheet and carry data into it. A client rule from the widget bootstrap configuration can open one at the right point in the experience. A server hook can open one when the conversation reaches a required step.</p>
<p>Those paths cover different jobs while keeping the shopper-facing interaction consistent. A button on a card can begin a flow. A configured rule can ask for information when a conversation starts. The server can require a step before work continues.</p>
<p>The first-message flow shows why this needed to be part of the conversation system. When a channel has a capture sheet, the visitor&#39;s first message is held locally while the sheet is active. The server enforces the gate, including attempts to skip or close a required step. A message sent through the host-page <code>sendMessage</code> API is routed through the same capture rule.</p>
<p>There should be one rule regardless of how a message enters the widget. Otherwise a required step becomes a suggestion with an easy bypass.</p>
<h2 id="contact-identity-as-the-first-built-in">Contact identity as the first built-in</h2><p>The first built-in on this surface is the contact identity form. It can collect a name, email address and phone number. Email and phone can include a one-time-code step when verification is configured.</p>
<p>The shopper remains in control of the contact data. The agent can nominate information for the form. The visitor confirms it in the sheet, code validates it and the system writes it. A server-only tracked event records the completed action.</p>
<p>Verification has its own operational controls. One-time codes are hashed before storage. Resends and incorrect attempts have per-conversation budgets. The implementation also applies ceilings by destination and workspace. Successful checks stamp the contact&#39;s email or phone verification time, which lets the product show a verified badge on that contact.</p>
<p>Delivery sits behind a transport. Crossword includes a built-in email verification tool for each workspace and supports merchant verification tools with API mapping. Those tools are managed under Tools, then Verification. A selected tool has to be usable before a sheet can be published.</p>
<p>This separation is deliberate. The sheet owns the interaction. The verification tool owns code delivery. The server owns enforcement and the final write.</p>
<h2 id="authored-with-the-cards-workflow">Authored with the cards workflow</h2><p>Teams author these stepped sheets in the dashboard under Cards. Publishing versions the configuration. A sheet can be attached to first-message capture, opened from a card button or opened during a handoff or agent-driven flow.</p>
<p>The release includes the general sheet surface and the contact verification flow. The underlying model can support other structured tasks through different content and submit targets. We kept this article focused on the built-in that shipped with the surface.</p>
<p><figure class="article-figure"><img src="/cw-draft-13ec83eda14bc2bc/media/sheet-builder/02-add-to-cart-sheet.png" alt="An add-to-cart sheet showing the shared surface applied to a product action." /><figcaption>An add-to-cart sheet showing the shared surface applied to a product action.</figcaption></figure></p>
<p>That product-action example is useful because it shows the boundary of the primitive. The sheet supplies focused space inside the widget while the content model defines the controls and action. A team can reuse the interaction pattern without creating another modal system for every task.</p>
<p>The important implementation detail is the gate. Required steps are checked on the server, close and skip refusals are handled there and the original message moves forward only after the sheet resolves. The widget also keeps its thinking indicator active beyond a sheet&#39;s closing line so the transition back into the agent response stays legible.</p>
<p>We now have one surface for structured work inside a Crossword conversation, with dashboard authoring, publish-time versioning and server enforcement connected to the same flow. The first built-in uses it to let a shopper confirm and, when configured, verify their contact identity before the held message is released and the conversation continues.</p>
