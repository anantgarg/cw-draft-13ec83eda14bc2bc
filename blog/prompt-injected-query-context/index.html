Put the right context inside the agent prompt

16 September 2026Released
The prompt is the attachment mapLive page context can participateAuthoring and runtime now share the same structure

We have been working on a basic question at Crossword: where business data should enter an AI shopping assistant's instructions.

The answer now lives in the prompt itself. An operator can place a query, table, knowledge source, context variable or memory reference by typing # and choosing from a categorized list. The resulting chip is the attachment. At runtime, requested context is injected at that mention site, exactly where the operator placed it in the instructions.

That placement matters. A prompt has structure. The sentences before and after a piece of context tell the model how to use it. If an operator writes an instruction around order data or product knowledge, the resolved context belongs inside that instruction. The author can see the relationship while editing instead of keeping a separate mental map of prompts and attachments.

The prompt is the attachment map

Typing # opens the mention editor. Its catalog groups skills and tools, knowledge, tables and queries, context variables and memory. Choosing an item creates an atomic chip in the text. The stored form remains a readable token such as #query/open-orders while the editor renders the human name.

This creates a direct contract. A mention enables the referenced capability for that agent. Removing the chip and saving removes the attachment. The publish path resolves the mentions and blocks publishing when a referenced item is broken or still needs setup. Drafts can still be saved while the operator fixes the configuration.

For tables, the chip also carries permissions. Read access is the default. Insert, update and write access are explicit modifiers shown in the editor. That makes a data grant visible during prompt review and keeps the instruction and its access decision in one place.

The same model works for stored queries. A query can remain available as a tool, provide results inside instructions or do both. Each binding controls its parameter mapping and refresh behavior. This gives the operator a useful choice: let the agent decide when to call a query, provide the result as part of the authored instruction or combine the two for a workflow that needs both.

Live page context can participate

Shopping conversations happen on a page with useful state. The shopper may be looking at a product, a cart or a section of a merchant site. Crossword already lets the host page send declared {{context.*}} values with the conversation. The message carries a snapshot for that turn so the agent works with the page context that accompanied the message.

Operators declare these variables per workspace with a type and flags such as required or sensitive. The declared catalog acts as an allowlist. String values are sanitized and sensitive values are redacted from logs and traces. Context variables are treated as untrusted reference data. They cannot authorize access or choose which customer's protected rows are visible.

Those values can also supply stored query parameters. The query path resolves them on the server from the run context, outside the model's arguments. If a referenced value is missing for the turn, the binding is skipped instead of allowing the model to invent it.

Customer identity follows a stricter path. Query parameters can use verified contact fields including the sign-in user ID, email and phone. Per-customer row scope comes only from the verified sign-in identity. An anonymous visitor does not resolve those fields. This separation lets page context describe the current experience while verified identity controls access to customer data.

Authoring and runtime now share the same structure

The editor stores mentions as plain text tokens. At publish time, Crossword resolves those tokens to workspace entities and records the attachment set. At runtime, prompt assembly renders the resolved value or capability at the token's position. The model receives context inside the instruction structure the operator wrote.

There are practical benefits for review. An operator can scan an instruction and see its dependencies. A deleted or unavailable reference has a visible chip state. Table write access is visible on its mention. Context variables appear alongside the instruction that consumes them. The prompt becomes a readable account of the agent's capabilities and inputs.

This work also joins several existing surfaces without presenting them as separate programming systems. Data Tables remain the place to define data and stored queries. Context Variables remain the contract for live host page state. The mention editor is where an operator composes those pieces into an agent's behavior.

For an ecommerce team, the result is a more precise way to build shopping assistance. A product question can be grounded with the selected knowledge source. An order instruction can use a stored query with verified customer scope. A page aware instruction can consume the context snapshot sent with that shopper's message. Each dependency sits where its meaning is clear in the prompt and Crossword resolves it under the corresponding runtime guardrails.
